## 工作流

### 1. 读取阶段
- 在开始执行任何排查/修复前，先读取 `ISSUE_TRACKER.md` 文件。
- 获取问题清单（✅ 已修复 / ❌ 未修复 / 🕒 待验证）。
- 仅处理 ❌ 和 🕒 条目，跳过 ✅。

### 2. 信息收集阶段（通用检查清单，强制执行）
在开始修复前，必须收集并记录以下信息（不依赖具体技术栈或服务）：
- 当前代码配置（含环境变量、构建参数）
- 客户端状态数据（如 localStorage / sessionStorage / 缓存 / Cookie）
- 网络请求日志（包含关键操作的请求与响应）
- 外部依赖或第三方服务的配置
- 用户操作历史（如是否清理缓存、修改配置、切换环境）

### 3. 全局分析
1. 对报错/异常进行 **全局溯源**：
   - 报错位置的调用链（函数调用、组件调用、依赖关系）。
   - 项目的配置文件、环境变量是否影响该行为。
   - 是否存在依赖库的已知 bug 或版本兼容问题。
   - 项目中是否有多个地方存在类似实现（可能的重复 bug）。
2. 输出一个 **可能根因列表**，并按概率从高到低排序。  
3. 禁止直接修复代码，只输出“分析报告”。

### 3. 根因候选生成
每个问题必须列出 **至少5个可能根因**，并用图标标注概率（示例概率分布，可按实际调整）：
1. 应用代码配置错误 (≈30%)
2. 环境变量或构建参数错误 (≈20%)  
3. 客户端缓存或状态污染问题 (≈25%)
4. 网络层或 CDN 缓存问题 (≈15%)
5. 外部依赖或第三方服务配置问题 (≈10%)

1. 明确区分 **根因** 和 **症状**：
   - 症状：只是报错表现，修复后可能掩盖问题。
   - 根因：问题的来源，一旦修复，所有相关症状都会消失。
2. 对每一个可能原因标记：[根因候选] 或 [症状]。
 错误现象可能是 **症状**，真正根因需要证据驱动  

### 4. 假设验证
为每个候选假设设计验证方法，明确：
- 可验证的步骤
- 支持/反驳证据
- 通过/失败条件

### 5. 修复阶段
1. 基于分析确认的 **根因**，提出修复方案。 
每次修复必须留下 **验证证据**  
2. 每个修复方案需包含：
   - 修改点（文件 / 函数 / 路由 / 组件）。
   - 具体修改思路。
   - 潜在副作用。

在修改之前，输出一份 checklist 并逐项确认：
- 是否存在相同问题在其他文件/模块中？
- 是否检查了配置文件和依赖库版本？
- 是否确认修改针对的是“根因”而不是“症状”？
- 是否评估了可能的副作用？

如果 checklist 未覆盖，请继续分析，而不是直接修复。
1. 在确认 checklist 全部通过后，再输出代码修复。  
2. 修复必须基于真实 API/服务，**禁止引入 mock 数据、本地降级方案、临时 patch**。  
3. 移除所有测试文件、调试残留（`console.log` / `alert` / `test` 文件 / mock 按钮）。

- 修复完成后，立即执行验证命令（示例）：
  - 构建验证（如 `npm run build`）
  - 静态检查（如 `npm run lint`）
  - 类型检查（如 `tsc --noEmit`）

步骤 6：二次验证
1. 扮演 **代码审查员**，重新审视修复方案：
   - 是否可能引入副作用？
   - 是否只是掩盖报错？
   - 是否存在更优雅的根因解决方案？
2. 给出最终确认意见。

### 7. 更新阶段
- 将修复状态写回 `ISSUE_TRACKER.md`：
  - ✅ 完全修复并验证通过  
  - 🕒 修复过但验证失败，需要进一步排查  
  - ❌ 修复未完成  
- 新发现的问题必须 **追加** 到清单，而不是覆盖。

### 8. 输出阶段
- 输出更新后的完整清单（同步 `ISSUE_TRACKER.md` 的内容）。
- 输出本次修复的详细 diff 和验证日志。

## 安全与纠偏机制

### 防止“一叶障目”
- 严禁只根据表面症状下结论。
- 必须明确区分 **症状** 与 **根因**。

### 客户端优先检查
- 涉及认证、状态或数据异常时，必须先检查客户端缓存与状态。
- 错误现象 ≠ 配置错误，可能是遗留或污染的缓存。

### 强制暂停机制
当同一问题连续两次修复失败时，必须：
1. 停止所有代码修改
2. 重新收集完整信息
3. 重新生成根因假设清单
4. 寻求替代角度或交叉验证
